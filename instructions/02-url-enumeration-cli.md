\# InfinityCrawler Task: Stage 02 URL Enumeration CLI

\#\# Objective

Add a deliberately small command-line application on top of the existing InfinityCrawler library so a user can provide a start URL and receive the discovered URLs within that URL's path subtree together with useful crawl status information.

The CLI must use the Stage 01 path-scoping feature rather than reimplementing crawl logic.

Example intent:

\`\`\`text  
InfinityCrawler.Cli https://example.com/ducks/  
\`\`\`

Expected style of output:

\`\`\`text  
\[200\] https://example.com/ducks/  
\[200\] https://example.com/ducks/mallard/  
\[301\] https://example.com/ducks/old/  
\[403\] https://example.com/ducks/private/  
\`\`\`

Exact status rendering may vary where the crawler exposes a non-HTTP terminal state, but output must remain concise and human-readable.

\#\# Constraints

\- Read \`AGENTS.md\` and \`G:\\My Drive\\Arden\\InfinityCrawler\\CONTEXT.md\` before editing.  
\- Preserve the Stage 01 implementation and its default library semantics.  
\- Do not redesign the crawler.  
\- Do not add a GUI, web UI, database, persistence layer, AI integration, graph visualizer, export subsystem, plugin framework, or other unrelated capability.  
\- Do not modify autogenerated \`\_Index\_of\_\*.md\` files.  
\- Do not attempt to fix the documented pre-existing \`net461\` assembly-binding issue.  
\- Prefer the .NET standard library and existing project dependencies. Do not introduce a command-line parsing package unless there is a compelling implementation reason.

\#\# Implementation Requirements

1\. Add a console application project named \`InfinityCrawler.Cli\` under \`src/\` and include it in \`InfinityCrawler.sln\`.  
2\. The CLI must reference the existing \`InfinityCrawler\` project directly.  
3\. The first positional argument is the required absolute HTTP or HTTPS start URL.  
4\. Scoped crawling must be enabled by default using \`CrawlSettings.RestrictCrawlToStartingPath \= true\`.  
5\. The CLI must not duplicate URL-discovery, path-matching, sitemap, robots, redirect, retry, or throttling logic already owned by the library.  
6\. Print one final result line per crawled/discovered URI after the crawl completes.  
7\. Each result line must include:  
   \- the URI  
   \- the most useful available status representation  
8\. For results with HTTP request history, use the final request's HTTP status code where available.  
9\. For crawler terminal states without a useful HTTP status code, render a short textual state such as \`ROBOTS\`, \`MAX-RETRIES\`, or equivalent based on the existing model. Do not invent misleading HTTP codes.  
10\. Output must be deterministic. Sort final result lines by URI using an ordinal comparison before printing.  
11\. Avoid duplicate output lines for the same final URI.  
12\. Support \`--help\` and \`-h\`.  
13\. With no URL argument, print concise usage information and return a non-zero exit code.  
14\. With a malformed, non-absolute, or non-HTTP/HTTPS URL, print a concise error to stderr and return a non-zero exit code without starting a crawl.  
15\. Return exit code \`0\` when the crawl operation completes normally, even if individual discovered URLs return 4xx/5xx responses. Those are crawl results, not CLI invocation failures.  
16\. Return a non-zero exit code for invalid arguments or an unhandled crawl-level failure.  
17\. Configure a clear CLI User-Agent rather than relying on the library's legacy default browser-like User-Agent. Use a simple identifier such as \`InfinityCrawler.Cli/1.0\` unless repository conventions suggest a better static value.  
18\. Keep request concurrency and polite crawling behavior on library defaults for this stage unless tests require zero-delay options.

\#\# Minimal Optional Argument

Add only one operational option in this stage:

\`\`\`text  
\--max-pages \<number\>  
\`\`\`

Requirements:

\- positive integer only  
\- maps directly to \`CrawlSettings.MaxNumberOfPagesToCrawl\`  
\- omitted means the existing unlimited/default behavior  
\- invalid values produce a concise stderr error and non-zero exit code

Do not add more CLI options in Stage 02\.

\#\# Usage Contract

The implemented usage should be conceptually equivalent to:

\`\`\`text  
InfinityCrawler.Cli \<url\> \[--max-pages \<number\>\]  
InfinityCrawler.Cli \--help  
\`\`\`

The exact executable invocation during development may be:

\`\`\`powershell  
dotnet run \--project src/InfinityCrawler.Cli \-- https://example.com/ducks/  
\`\`\`

\#\# Status Rendering

Inspect the existing \`CrawledUri\`, request history, redirect data, and \`CrawlStatus\` model before implementing output rendering.

Rules:

1\. If a result has a final request with an HTTP status code, print the numeric HTTP status.  
2\. Otherwise map the existing crawler terminal state to a short stable text label.  
3\. Do not infer success merely from \`CrawlStatus.Crawled\`; a crawled URI may have returned a non-2xx status.  
4\. Do not alter library result models solely to make CLI formatting convenient unless there is a genuine blocker. If a library change is required, keep it minimal and explain it in the report.

\#\# Testing Requirements

Add automated tests for the CLI's argument parsing and result/status formatting. Keep parsing/formatting logic separable enough to test without making real external web requests.

Tests must cover at minimum:

\- valid absolute HTTP URL accepted  
\- valid absolute HTTPS URL accepted  
\- malformed URL rejected  
\- relative URL rejected  
\- non-HTTP scheme rejected  
\- no arguments returns usage/error behavior  
\- \`--help\` behavior  
\- valid \`--max-pages\` value  
\- zero \`--max-pages\` rejected  
\- negative \`--max-pages\` rejected  
\- non-numeric \`--max-pages\` rejected  
\- deterministic URI sorting  
\- HTTP status code rendering from the final request  
\- crawler terminal-state rendering when no HTTP status exists

If practical within the existing test architecture, add one integration-style test using the in-process TestSite to verify that invoking the CLI crawl logic against a nested start path does not enumerate out-of-scope sibling URLs. Do not create a brittle subprocess-based test merely to satisfy this point; prefer testing extracted CLI application logic directly.
